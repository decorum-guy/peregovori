## Зачем

Показать Юрию Клименко, сооснователю и главному методологу Soft Skills Lab, **полноценную, визуально аккуратную, играбельную** концепцию нового инструмента практики, потенциально дополняющего библиотеку игр. Это независимый прототип и предложение к сотрудничеству; **не официальный сайт школы, не её продукт и не утверждённое зеркало**.

Встреча: демонстрировать не графики fine-tuning, а опыт игрока: **выбрал параметры → получил уникальный обоснованный кейс → сыграл живой диалог → увидел корректный разбор**. Исследовательские результаты 8B/QLoRA показывать дополнительным экраном по запросу.

## P0: необходимые пользовательские пути

**1. Старт/выбор** — максимум один компактный экран:
- Имя игрока (не обязательно; дефолт «Вы»; не запрашивать реальные данные без нужды).
- Главный переключатель (РОВНО три варианта): **Конфликт / Переговоры / Конфликт + переговоры**. Третий — сценарий, в котором конфликт может влиять на рациональные переговоры и стороны возвращаются к ним при снижении напряжения. Не путать его со смешанным типом конфликта.
- При «Конфликт» И «Конфликт + переговоры»: тип **личный / публичный / смешанный**. Это классификация типа конфликта по методологии курса, а не переключатель режима. Для «Переговоров» это поле скрывается.
- Сложность: easy / medium / hard / extra_hard / impossible; дружелюбные названия, точное значение сохраняется. Impossible = определённый желаемый исход закрыт по объективной причине, а не бесконечный отказ.
- Сфера: работа / семья / учёба / друзья / другое; пользовательский текст при «другое».
- **За кого играет пользователь:** «Защищаю границы» / «Оказываю давление»; в чистых переговорах не нужен (обе стороны договариваются). При защите студента ИИ = `MODEL_MANIPULATOR`; при давлении студента ИИ = `MODEL_DEFENDER`. Это направление нельзя перепутать.
- Ролевая модель: **«Claude Opus 5.5»** (основной API через OpenRouter, сильнейший класс Claude/GPT) / **«Qwen3-8B · Дообученная»** (реальная LoRA, только если подключён и проверен сервер). Альтернативный флаг конфигурации для премиум API: `openai/gpt-6-astra` («GPT-6 Astra»). В UI **ровно две** модели на выбор, никакой третьей опции. **Никакой Qwen3-32B в качестве премиального API-собеседника.** НЕ выдавать стандартную 8B за LoRA. Если LoRA недоступна — явно показать недоступность, не подменять молча.
- **«Случайно»** заполняет режим, тип (если конфликт), сложность, сферу, роль пользователя (если конфликт); сохраняет имя и выбранную модель. При «Другое» появляется необязательное поле собственной темы/ситуации.
- **«Начать игру»** — реальная генерация кейса с сервера, с loader и retry; никакой заранее нарисованной фейковой генерации.

**2. Игровой экран** — привлекательно и без визуального мусора:
- Публичная обстановка, роль, цель, известные игроку факты. Данные оппонента private и педагогический эталон не показываются.
- Чат как мессенджер: имя персонажа слева, игрока справа; автопрокрутка, несколько абзацев, адаптивно; Enter отправить / Shift+Enter перенос; loading, graceful API errors, запрет двойных отправок.
- Первое сообщение = `opponent.opening`; никакого приветственного текста LLM вне роли.
- Кнопка **«Завершить» доступна всегда**, в том числе после одного сообщения. Бэкенд фиксирует завершение, прекращает игровые реплики, затем показывает отдельный экран-предложение: «Хотите получить оценку и рекомендации?» → **«Получить разбор» / «Завершить без оценки»**. Если отказ — НЕ вызывать Judge API и НЕ списывать за него токены. Возможность разборa позже по сохранённой завершённой сессии — полезно, но не блокирует P0.
- Пауза/заметки/подсказки из исходного MVP — **P1**, не должны задержать P0.

**3. Разбор по запросу, а не автоматически**
- Только если пользователь явно выбрал «Получить разбор»: сильная API-модель в роли Judge, отдельно от действующего персонажа; сводка + сильные ходы + рискованные ходы + следующий шаг с привязкой к фактическим репликам и методологии школы.
- Не выдавать субъективный скор за экзаменационный балл школы. Не раскрывать скрытые мотивы противника в середине игры; в конце раскрывать только настолько, насколько оправдан разбором.
- Если игрок завершил рано, Judge осторожно отмечает, что выводы ограничены коротким диалогом, а не наказывает за отсутствие непройденных этапов.
- Позволить «Сыграть ещё» из настроек. Никакой обязательной регистрации.

**4. Галерея игр**
- После проверки оригинальной страницы сохранить реальные названия/URL чужих игр в корректных карточках, ведущих НА оригинал; добавить **свою** карточку «Переговоры и конфликты».
- Визуально вписаться, но без поддельного официального сайта, без копирования чужого кода/ассетов.
- Если страница-референс недоступна — собственная аккуратная галерея + наша игра, без выдуманных чужих продуктов.

## Внутренняя логика: экономно по токенам и предсказуемо

1. **Case generator**: один API-вызов сильной модели после «Начать». Вход: параметры UI + **сжатые** `course_sot/compact_runtime_spec.yaml` и relevant `techniques.yaml`/правила по режиму + существующий `schemas/case.schema.json`/конкретная целевая JSON-схема. Не отправлять все PDF и транскрипты каждый раз. Получить одно валидное `case`, validate, один repair retry при ошибке; затем аккуратное fallback из **TRAIN/public accepted case**, не из DEV/TEST. Можно заранее иметь 5–10 демонстрационных проверенных стартовых кейсов для резервного пути. Отличать reused fallback от реальной генерации в диагностике.
2. **Roleplayer**: ровно **один выбранный в начале игры движок ведёт ВСЕ игровые ходы до завершения**, без подмены движка посреди разговора. Для премиальной модели это `anthropic/claude-opus-5.5` через OpenRouter (или вручную через env `openai/gpt-6-astra`), для пользовательской LoRA — действительный Qwen3-8B LoRA endpoint. Одна и та же карточка кейса, история, world established facts, private opponent/limits, правила `training/prepare_sft.py:model_context()` на обоих движках. НИКОГДА не подавать `teaching`/правильный ответ roleplayer; не загружать лекции в каждую реплику; не перегружать модель системой и не заменять private facts публичными. Строго один ход персонажа, русский, нет мета-советов.
3. **Judge/Coach**: только после «Завершить» **и согласия пользователя** — отдельный API-вызов мощной Claude/GPT через OpenRouter + компактный курс + педагогическая разметка и лог игры; подсказки P1. Иначе ни одного judge-вызова.
4. **Зрители** для публичного и смешанного конфликта: на P0 зафиксировать имена/контекст 1–2 участников аудитории в кейсе. Если генерируем отдельные реплики аудитории, их делает **тот же выбранный Roleplayer**, что ведёт основного оппонента (одним ответом со структурированными `speaker`/`text` или отдельным вызовом ТОЛЬКО выбранного движка); **никогда не переключать игру на API-модель, если игрок выбрал LoRA**. Минимальный P0: публика присутствует в описании/ролевой сцене, без толпы-агентов. Для режима «Конфликт + переговоры» на высоких сложностях вероятность реалистичной эмоциональной эскалации выше, но по смысловым триггерам и мотивации, не случайный срыв вопреки сценарию. Реплики аудитории не должны заменять модель оппонента или нарушать историю/приватность.
5. Сохранять состояние на **сервере**, в SQLite/минимальном хранилище. Browser получает только публичную часть и свои сообщения. Не передавать секреты API клиенту. Короткая память по истории и редкие summary при необходимости; для ~6–12-ходового демо полный диалог дешёв.
6. **Сильная облачная модель (НЕ Qwen)** через OpenRouter-совместимый эндпоинт. Подтверждённый модельный ID: `anthropic/claude-opus-5.5` (основной рекомендуемый вариант), допустимый премиум-заменитель `openai/gpt-6-astra`. Изменять через `PREMIUM_MODEL`/`CASE_MODEL`/`JUDGE_MODEL` в env, не добавляя в UI третью модель; все три по умолчанию могут быть одной и той же Claude Opus 5.5, но разные системные инструкции. `OPENROUTER_API_KEY`, `LORA_BASE_URL` — **только на сервере**. Проверить актуальные API-модельные ID и цены до запуска (источники: https://openrouter.ai/anthropic/claude-opus-5.5 и https://openrouter.ai/openai/gpt-6-astra).
7. Текущая QLoRA V1 на Qwen3-8B обучена и DEV-проверена, но **не развернута как внешний HTTP endpoint**. Intelion GPU была остановлена; автономная LoRA через браузер не заработает без отдельного serving. P0 cloud полностью рабочий, P1 реальный GPU-serving с ограничением стоимости/времени на встречу. Не держать 3090 включённой бессрочно.
8. Никакого RAG, embeddings, векторных баз, агентных оркестраторов, multi-agent crowd swarm, fine-tuning нового генератора или интернет-поиска в диалоге до демонстрации.

## Технологический маршрут: один деплой

Рекомендуется UI `React + Vite + TypeScript + Tailwind` (аккуратно, без тяжёлых компонентов) + имеющийся в архитектуре простой `FastAPI + SQLite`; собирать frontend и раздавать через тот же FastAPI/контейнер. Один HTTPS-домен/один backend, минимальный Dockerfile. Разместить на одном малом PaaS (Render/Railway или аналог с понятным HTTPS) — НЕ на дорогом постоянном RTX 3090. OpenRouter key только на сервере. Допустима другая единая реализация, если Codex докажет, что она объективно быстрее и проще и не потеряет серверную приватность.

**Сначала localhost full vertical slice**, после рабочего первого кейса — деплой на временный URL, затем домен. DNS — не критический путь; если домен долго распространяется, показываем временный HTTPS-адрес.

## Жёсткий дедлайн и дорожная карта (~46 часов)

- **0–3 ч:** Codex визуальный аудит gallery + main; краткая карта компонентов, скриншоты/блокер и 1 экран проектирования. 30–45 минут потолок на попытку открыть игры; если не вышло — просим screenshots, не стопоримся.
- **3–12 ч:** настоящий работающий вертикальный срез: экран → генерация кейса → первая реплика → 3–5 обменов → завершение/разбор через API. Испытать server secret и отсутствие leak.
- **12–25 ч:** UX, адаптивность, галерея (только подтверждённые ссылки), стабильная обработка ошибок, минимальная запись сессии и перезапуск, развёртывание по HTTPS.
- **25–35 ч:** улучшить промпты/динамику, малый smoke-набор 6 сценариев (личный, публичный, смешанный × простая/сложная реакция), проверить impossible без капризного infinite loop.
- **35–41 ч:** если P0 жив, подключить Intelion QLoRA как ВТОРОЙ реально рабочий движок или корректно пометить «недоступна»; проверить безопасность/стоимость/связь по HTTPS. Никакого нового fine-tuning до P0.
- **Последние ≥5 ч:** только regression, визуальная полировка, запись резервного видео демо, презентация и проверка домена/HTTPS/оплаты API. ЖЁСТКИЙ feature freeze.

**GPT-6.1 Sol** — постановка архитектуры/первые решения, работа с сложными багами, финальное ревью. **GPT-6 Luna** — длинные ночные задачи по конкретному контракту, многокомпонентная реализация и тесты. Не проводить обеими моделями одновременные непроверенные переписывания одного набора файлов; каждый этап завершать коммитом и проверкой.

## Три изолированные роли одной сильной API-модели — однозначный контракт

```text
«Начать»  → Case Generator [OpenRouter Claude/GPT] → runtime case JSON + public case card
Игровой ход → ровно выбранный Roleplayer [Claude/GPT ИЛИ Qwen3-8B QLoRA] → ответ персонажа
«Завершить» → закрытие игры, без вызова модели
«Получить оценку» → Judge [OpenRouter Claude/GPT] → учебный разбор
«Без оценки» → назад, zero Judge tokens
```

Игрок не выбирает генератор или Judge. Игрок выбирает **только одну из двух моделей собеседника**. Generator/Judge — внутренние вызовы одной мощной API-модели с **разными промптами**, не самостоятельные чат-оппоненты. При смене `PREMIUM_MODEL` UI переименовывает соответствующий вариант динамически из конфигурации backend.

Действующая схема `schemas/case.schema.json` предназначена для **полностью размеченного TRAIN кейса с готовым `dialogue` минимум из 4 сообщений**. Runtime-генератор НЕ должен сочинять всю игру заранее или подсовывать игроку `dialogue`. Сделать минимальный runtime контракт (`public/world/opponent/teaching/category/scenario/difficulty`) и отдельный валидатор/конвертер по существующим полям; сессия с UUID отдельно. `world`, `opponent.private_facts`, `opponent.hard_limits`, `teaching` остаются только backend. Контекст игрового движка получает собственные скрытые ограничения оппонента, но **НЕ** `teaching` и НЕ эталонные ответы.

Оценивание: использовать исходные рубрики `course_sot/evaluation_rubric.yaml` (раздельно наблюдаемые навыки, без искусственного «общего экзаменационного балла»), `compact_runtime_spec.yaml`, relevant `techniques.yaml`, индивидуальный `teaching`, историю реальных реплик, объяснения с привязкой к цитатам. Для короткого диалога честно указывать ограничение данных. Все оценки после игры — рекомендации независимого прототипа, не официальный балл Soft Skills Lab.

Не тащить весь курс на каждый turn. На Generator/Judge передавать **версионированную сжатую методологию** на 4–8 KB (из локальных `course_sot/`), режимно-релевантные техники, критические ограничения и конкретный кейс/историю; cache доступных неизменных префиксов по возможностям провайдера. Roleplayer только case+history+role rules (без PDF/RAG). RAG/эмбеддинги отложены, пока реальные промахи в курсе не доказали необходимость.

**Защита UX:** каждый API-вызов — один понятный loader и retry, timeout, читаемые ошибки, строгая серверная валидация, ограничение числа ходов/токенов/частоты, no raw API secrets or prompt dumps in console. «Случайно» — UI-рандомизатор параметров, а не принудительная отдельная генерация до «Начать». Если нужный эндпоинт LoRA недоступен — честно disabled, никогда не отдавать за неё ответы Claude.

## Стадии Codex и внешний дизайн

1. Sol: архитектурный контроль и первичная задача `prompts/CODEX_DESIGN_AUDIT.md` — открыть фактическую библиотеку игр в браузере (или бережно сохранить HTML/CSS/скриншоты), создать мини-брендбук/компоненты; **не выдавать зеркало за официальный сайт**. Время на невозможный доступ — 30–45 минут, затем скриншоты от пользователя.
2. Codex: вертикальный срез Generator → Chat (премиальный Claude/GPT) → завершение → **по желанию** Judge. Сначала энд-ту-энд работа, затем сложная красота.
3. Luna: остальной front/back, мобильные состояния, минимальная аудитория, галерея с реальными ссылками, раздельные состояния ошибки/повтора.
4. Sol: интеграционное тестирование, безопасность, домен/деплой/демонстрационная полировка. Не менять файлы параллельно без общего commit/checkpoint.
5. LoRA endpoint — параллельная ветка, **не задерживает работающий премиальный путь**; новое fine-tuning не является P0 до встречи.

Бизнес/авторство: независимый proof of concept с собственной карточкой игры, рядом — **ссылки на оригинальные игры**. Зеркалировать чужие страницы, логотипы, CSS, JS, тексты и размещать их под своим доменом **только с разрешения владельца**. До разрешения — визуальный референс, а не публикация клона.
