# Архитектура MVP — минимально необходимая

## Два назначения LLM

**1. Case Generator (offline)** — сильная модель создаёт кейсы заранее, партиями. Её выход проверяет независимый валидатор. В живой сессии этот компонент **не вызывается**.

**2. Roleplayer (runtime)** — Qwen3-8B (сначала базовая, потом QLoRA при доказанном выигрыше) играет одного персонажа строго по карточке кейса и состоянию диалога. Не выступает преподавателем во время игры.

**Judge/Coach — не третья постоянно работающая модель:** это отдельный аналитический вызов API с другим промптом/контекстом по запросу подсказки, проверки или разбора. Может использовать отдельную более сильную LLM. Нельзя доверять самосуду roleplayer.

## Один сервер приложения

Для MVP достаточно **Python FastAPI + SQLite + простая веб-страница (HTML/CSS/JS)**. Позже фронтенд можно заменить без изменения контракта. Не нужны микросервисы, отдельные очереди, векторная БД, Kubernetes или сложная событийная шина.

```text
  Сильная LLM → генерация CASE JSON → внешняя LLM-проверка → 200 принятых кейсов
                                                                |
  Студент в браузере ←→ FastAPI (один backend) ←→ SQLite / JSON-кейсы
                          |      |     |
                          |      |     └─ скрытый эталон/история/заметки
                          |      └─ Judge/Coach (отдельный вызов, по необходимости)
                          └─ Qwen3-8B Roleplayer (реплика в чате)
```

## Один ход

1. Бэкенд читает `case`, текущий `session`, историю реплик.
2. Студент может сохранить заметки: это **не раскрывает** ответы и не меняет поведение персонажа само по себе.
3. Студент отправляет реплику. Roleplayer получает установленные факты, приватные интересы СВОЕГО персонажа, актуальное состояние и историю. Он **не получает скрытый педагогический эталон или заметки как истину**.
4. Roleplayer отвечает **только в роли**. Бэкенд сохраняет ответ.
5. По запросу Judge/Coach оценивает действия студента по фактам, рубрике, курсу и истории, выдаёт подсказку/разбор отдельно от диалога.

Для первого MVP допустимо хранить `session` как обычный JSON в SQLite. Не нужна отдельная машина из десятков таблиц. `phase` = `conflict` / `negotiation` / `finished` / `stage4`, плюс обновляемые `emotion`, `pressure`, `revealed_facts`. Изменения динамики проверяются правилами кейса и оценкой Judge при необходимости.

## Границы доверия

- Browser получает **только публичную карточку**, собственные заметки, историю и разрешённые подсказки.
- Private opponent facts, условия уступок и `teaching` остаются на сервере.
- Кейс задаёт факты; модель не имеет права добавлять как исторически существующие имена, цифры, встречи, регуляции и документы, которых нет в мире кейса.
- Неизвестное остаётся неизвестным. **Новые предложения/условные гипотезы** допустимы, если не выдаются за уже случившиеся события.
- Сложность не отменяет последовательность ролей, фактов и реакций.
- Подсказка не влияет на реакцию оппонента через скрытые метки; оппонент реагирует на **сказанную студентом фразу**.

## Технологии / деплой

- UI: статические HTML/CSS/JS, responsive.
- Backend: FastAPI, SQLite, JSON Schema validator.
- Model endpoint: OpenAI-compatible API, облачный или локальный; доступ/ключ хранится на сервере.
- Training: отдельный offline QLoRA эксперимент; данные только после PASS валидатора.
- Деплой MVP: один процесс/сервер + эндпоинт модели, без обязательного GPU в веб-приложении.

Никакой масштабируемости «на миллион студентов» до доказательства работающего MVP.
