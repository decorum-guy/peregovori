# Контракт публичной сводки кейса для DEMO 48H

**Решение владельца, 13 октября 2026. P0 — обязательное для первого рабочего vertical slice.** Утверждённый GPT Images-референс хранится в `docs/design_refs/line_of_decision_gpt_images_v1.png`, но **визуальная картинка не является контрактом полей**. Источник методологии: `course_sot/course_spec.yaml`, `course_sot/compact_runtime_spec.yaml`, `course_sot/state_machine.yaml`. Отдельный источник структуры закрытых TRAIN кейсов: `schemas/case.schema.json`.

## Зачем

В курсе **«тема на переговоры» и «цель на конфликт» — разные сущности**:
- *Тема на переговоры* — предмет рационального обсуждения: о чём надо договориться.
- *Цель на конфликт* — желаемое изменение границы / отношений / публичной неформальной роли, **с точки зрения того, чью цель показываем**.

Нельзя объединять их в единственное поле «Ваша цель», подменять одно другим или писать название «Цель конфликта» над внутренней задачей оппонента. Особенно это критично для `MODEL_DEFENDER`: в закрытом `teaching.conflict_goal` может описываться **цель защищающегося ИИ**, а не студента.

## Структура экрана: компактная сводка рядом с чатом

Требования к видимым секциям (никакой простыни с полями внутри скриншота GPT Images):

1. **Ситуация** — короткий `public.title` + `public.context`.
2. **Ваша роль** — `public.student_role`.
3. **Тема на переговоры** — `public.negotiation_topic`, если есть отдельный рациональный предмет, известный игроку.
4. **Цель на конфликт** — `public.player_conflict_goal`, только при конфликте, с позиции **игрока**, не оппонента. Без педагогических «ответов» и правильного приёма.
5. **Ваша задача** — `public.student_goal` только если добавляет смысл, отличный от двух пунктов выше; не повторять заголовки и текст.
6. **Известные факты** — `public.known_facts[]`, только то, что в рамках сюжета знает игрок.
7. **Участники** — имена/роли, которые игроку открыты по легенде; при публичном/смешанном типе указать аудиторию/свидетелей, не раскрывая их приватных реакций.
8. **Тип конфликта** (необязательно маленьким метатекстом) — личный/публичный/смешанный. **НЕ** подменять переключатель сценария «Конфликт + переговоры» типом «смешанный конфликт».

### Режимы

- **`negotiation_only`:** `negotiation_topic` обязателен и виден; `player_conflict_goal` = `null` и поле вообще скрыто.
- **`conflict_then_negotiation`:** оба поля обязательны, ОБА отображаются рядом/один под другим; цели должны быть логически различны, конфликт может возвращаться во время переговоров.
- **`conflict_only`:** `player_conflict_goal` обязателен и виден; `negotiation_topic` опционален: если нет отдельного рационального вопроса, = `null` и секция скрыта. Если рациональная тема действительно существует и известна игроку — показать.
- Для `MODEL_MANIPULATOR` (ИИ давит, игрок защищает) `player_conflict_goal` формулируется **для защищающегося студента**. Для `MODEL_DEFENDER` (игрок оказывает давление, ИИ защищает) `player_conflict_goal` — заявленная/ситуационно известная задача **самого игрока**, НЕ скрытая цель защищающегося ИИ.
- «Сложность impossible» не выдаёт игроку полный приватный алгоритм отказов или скрытую причину недостижимости конкретного исхода; публично объясняем только его фактическую ситуацию.

## Схема: separate runtime contract, НЕ менять frozen TRAIN

В `schemas/case.schema.json` сейчас `public` имеет `title/context/student_role/student_goal/known_facts`, а `teaching.negotiation_topic` и `teaching.conflict_goal` — **закрытый эталон**. Для демо вводится отдельная runtime-модель/Pydantic/schema, включающая:

```json
{
  "public": {
    "title": "Спор о запуске проекта",
    "context": "Руководитель требует отчёт уже завтра. Вы отвечаете за реалистичное планирование.",
    "student_role": "Руководитель команды",
    "student_goal": "Сохранить рабочие отношения и согласовать выполнимые обязательства",
    "negotiation_topic": "Сроки и объём отчёта",
    "player_conflict_goal": "Чтобы со мной согласовывали сроки без угроз и обесценивания",
    "known_facts": ["Полный отчёт требует ещё два рабочих дня"],
    "participants": [{"name": "Марина", "role": "Руководитель проекта"}]
  }
}
```

Пример иллюстрирует **формат**, а не готовый кейс и не эталон техники. Скрытые части того же runtime кейса (только backend): `world`, `opponent.private_facts/goals/hard_limits/concede_if/escalate_if`, `teaching`, внутреннее состояние/ограничения. Если нужна новая схема файла — `schemas/runtime_case.schema.json` или Pydantic-модель; оставить замороженную тренировочную схему и TRAIN/DEV/TEST без изменений.

**Генератор API** формирует публичные `negotiation_topic` / `player_conflict_goal` **отдельно** от закрытых `teaching` полей; проверка модели/JSON Schema/логики должна удостоверяться в правильном ракурсе (player vs model) и отсутствии раскрытия закрытого. Не «восстанавливать» UI-поля простым копированием `teaching` и не передавать всего `case` в ответ API. При несогласованности — 1 retry/repair, затем валидный резервный кейс с заранее подготовленными публичными полями.

**Публичный API** отдаёт whitelist именно этих пользовательских полей + безопасную историю, имя оппонента, выбранную модель. Не отдаёт `world` целиком, `opponent` целиком, `teaching`, внутреннюю system-инструкцию, ключи или приватные состояния. На `GET /api/sessions/{id}` тот же whitelist, чтобы refresh не приводил к утечке.

## UI / responsive

- По утверждённому `docs/BRANDBOOK_DEMO.md`: desktop боковая колонка ~280–320 px; её ширина не должна душить чат, чат >60% доступной области. В длинной ситуации можно прокручивать/сворачивать **известные факты** и вторичные детали.
- **Два смысла всегда различимы**: «Тема на переговоры» и «Цель на конфликт», с разными подписями и spacing. Не заменять их словом «Цель», не отображать закрытую цель оппонента.
- На мобильном: под заголовком краткая карточка ситуации с **видимыми заголовками и краткими строками по теме и цели** (если применимы), остальной контекст в доступной свёртке «Ситуация и факты». Публичная цель не должна исчезать навсегда за плохо заметной иконкой.
- Не добавлять скрытый этап «правильный конфликт/переговоры», подсказку метода, шкалу эмоций или раскрытие `teaching` — это отдельная фаза Judge **после согласия на разбор**.

## Проверки — обязательные авто- и ручные

1. Сгенерировать `negotiation_only`: нет пустого блока «Цель на конфликт» в DOM/JSON, «Тема на переговоры» конкретна.
2. Сгенерировать `conflict_only`: есть «Цель на конфликт» от лица игрока; если переговорной темы нет, нет пустого поля и нельзя вставлять закрытый `teaching.negotiation_topic`.
3. Сгенерировать `conflict_then_negotiation`: обе цели существуют, различимы по смыслу, видны в summary.
4. `MODEL_DEFENDER`: нельзя показывать противниковую цель из `teaching` как цель студента.
5. Публичный/смешанный конфликт: известные участники видны, private не видны.
6. `GET/POST` сериализация: ни `teaching`, ни `opponent.private_facts`, ни `concede_if`, ни `hard_limits`, ни `world.unknowns` не отдаются в browser.
7. Проверить 1440×900 и 390×844, длинные русские слова, полное восстановление после refresh.
8. Референс-картинка может иметь неточные отступы/поля — следовать токенам брендбука, реальной сетке и правилам этого файла.

**При конфликте требований:** `docs/DEMO_48H.md` и этот контракт > `docs/BRANDBOOK_DEMO.md` > GPT Images PNG. Методология `course_sot/` остаётся source of truth, никто не должен «допридумывать» её трактовку.
