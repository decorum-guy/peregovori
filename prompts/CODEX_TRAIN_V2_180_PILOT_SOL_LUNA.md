## 3. Только 8 новых игровых кейсов

Сбалансированный pilot:
- 3 `negotiation_only` (MODEL_NEGOTIATOR);
- 3 `conflict_only` (оба MODEL_MANIPULATOR и MODEL_DEFENDER);
- 2 `conflict_then_negotiation` (обе конфликтные роли);
- все пять `easy,medium,hard,extra_hard,impossible` хотя бы по одному; несколько personal/public/mixed, со свидетелями/аудиторией когда требуется.

Sol пишет полный `RuntimeCase` схемы `runtime-1.0`, включая достаточные established facts/unknowns, opponent private_facts/goals, hard_limits, concede_if/escalate_if, отстранённую/нейтральную public role, и единственную opening. У каждого кейса 3 **содержательно разные** независимые ветви: компетентный студент / ошибка или давление / неожиданный поворот. В каждой ветви 4 player→opponent пары **ПОСЛЕ** opening. Итого ровно 8 case cards, 24 branch records, 96 supervised assistant replies **при полном принятии**. История: opponent opening, player1, opponent1,...,player4,opponent4 (9 messages). Не смешивать три разные ветви в одну историю.

Sol отвечает за **всю художественную и смысловую целостность** кейса и targets; Luna **100% каждой ветви** оценивает отдельно, не видя Sol self-grade. Для REVISE/REJECT Sol переписывает, затем механическая и независимая Luna проверка повторяются. Автор не присваивает собственным ответам независимый PASS. Для спорных severe cases STOP и запрос человеческого решения, НЕ новый внешний платный reviewer.

## 4. Prompt parity: не путай с выбором Sol/Luna

Для будущего Qwen должен использоваться *точно действующий* стиль системного промпта **A** через `app.prompts.roleplay_messages` → `app.roleplay_contract.future_sft`. Это инструкция будущему игровому оппоненту, НЕ промпт Sol-генератора. `spoken-dialogue-1.0` пока нельзя включать в production, **но targets исключительно произнесённые слова** (без `*ремарок*`, Markdown, повествователя, `<think>`, подсказок игроку и больше одного вопроса). Не вставлять список десяти техник в RP контекст. Для tokenizer Qwen suffix добавляется ОДИН раз; HTTP его добавит сервер.

`teaching` корректно присутствует во внутренней полной `RuntimeCase` для будущего Judge; не должен оказаться в roleplayer prompt/target. Не проверять наивно, что строка «teaching» никогда не присутствует в самом тексте системных правил: действующий RP prompt запрещает её раскрывать, и это допустимо. Проверять именно наличие закрытых ПОЛЕЙ и СОДЕРЖИМОГО gold в serialized messages.

## 5. Проверка

100% Python CPU validator: Pydantic schema, group IDs, фактические квоты, `RuntimeCase`, branch scenario/role/mode, различение `public.negotiation_topic` и `public.player_conflict_goal`, корректная история и opening, `future_sft()` → **96** labels, никакой gold в prompt/target, Qwen suffix once, оригинальный сайт-производный serializer, manifest hashes.

Отдельный числовой/фактологический ledger: источник каждого имени, предмета, утверждения о прошлом, правомочия/обещания третьего лица, единицы измерения/сроки, арифметика после изменения условия. Python проверяет вычислимые части, Luna — семантику прав, публичного repair и фактологию unknown vs known. Текстологически запрети звёздочные ремарки, мета-обучение, самопрезентацию ИИ; один вопрос на реплику. Нельзя считать «не произошло в прошлом» эквивалентом «уже произошло». Нельзя принуждать impossible к уступке.

Luna отдельно проверяет: роль, пол/грамматические окончания при неизвестном поле, устойчивость интересов, уступки после реального выполнения `concede_if`, границы `hard_limits`, угрозы/публичную репутацию, отсутствие деталей вне кейса, естественность зрелой беседы и четыре настоящих причинно-связанных хода. В случае критической ошибки — REVISE/REJECT независимо от формальной схемы. Не «подчищай» отвергнутые ответные реплики программным stripping и не выпускай их как gold.
