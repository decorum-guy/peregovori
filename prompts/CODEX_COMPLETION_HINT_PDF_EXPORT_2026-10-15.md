## Задача B — необязательное предложение завершить кейс по достижении цели
Пользовательский смысл: после успешно полученного ответа персонажа, если цель игрока действительно подтверждена диалогом, внутри ленты чата появляется компактное отдельное НЕигровое сообщение «Модератор»: «Кажется, вы достигли цели этого кейса. Хотите завершить диалог?» Кнопки «Да, завершить» / «Нет, продолжить».
- «Да»: вызвать существующий `/finish`; потом прежний экран выбора «Получить разбор» / «Завершить без оценки». Не вызывать `/debrief` автоматически.
- «Нет»: оставаться в active и продолжать обычный диалог, сохранённый черновик не терять; избегать повторного предложения на той же реплике и навязчивых повторов. Не создавать фейковую реплику персонажа и не включать модератора в историю двух собеседников, промпт собеседника, расчёт количества ходов или экспорт текста беседы.
- Ручная кнопка «Завершить» остаётся всегда. Нет автоматического закрытия сессии, даже если детектор ошибся.
- Восстановление сессии после refresh / другого окна должно сохранять статус подсказки и отказа. С учётом гонок запросов: не показывать hint, пока ответ pending/failed/cancelled, пока операция finish/debrief идёт, либо когда сессия уже завершена; повторный запрос с тем же request_id не должен давать новый платный детектор и повторную подсказку.
- Определение достижения цели должно учитывать публичные `player_conflict_goal`, `student_goal`, `negotiation_topic`, `known_facts` (только релевантные и безопасные для игрока поля), `scenario`, `difficulty` и фактические подтверждения в ДИАЛОГЕ, особенно последнее сообщение противной стороны. Не считать успехом вежливую интонацию, «ладно», частичную уступку, пустое согласие, гипотетическое обещание или согласие игрока без изменения позиции персонажа. Для очень сложных/невозможных кейсов особенно требовать проверяемого результата; недостижимая цель сама по себе не может считаться выполненной.
- Сделать проверку семантической, а не regex-only и не доверять самоотметке roleplayer. Предпочтительный вариант: конфигурируемый, ограниченный по количеству и стоимости отдельный completion-check (после достаточного количества успешных ходов, например не ранее 3 реплик игрока), с коротким JSON-ответом `status: achieved|partial|not_achieved|uncertain`, оценкой уверенности и доказательствами, с безопасной строгой серверной валидацией; показывать подсказку только при однозначном `achieved` с достаточной уверенностью и текстовым подтверждением. Реализуй понятную оптимизацию числа запросов (например cooldown/предфильтр), чтобы не оценивать каждый токен или каждую реплику без ограничений. Модель и лимиты — явная конфигурация, никакого непроверенного hardcoded ID; использование дополнительного API нужно учитывать в usage/cost telemetry и документации; при ошибке/тайм-ауте детектора игра просто продолжается.
- Для Qwen без отдельного согласия на платную проверку через OpenRouter не делать скрытый premium call; допустимо оставить только ручное завершение, если локальную семантическую проверку обеспечить нельзя, с описанием ограничения.
- Состояние подсказки хранить на backend и возвращать в безопасном snapshot, не показывая hidden `runtime_case`, private_facts и teaching-секреты. Возможно отдельный endpoint для dismiss/evaluate — выбери простую архитектуру с безопасным idempotency и отсутствием гонок. Никогда не интерпретировать генерируемую персонажем фразу «ты достиг цели» как системную команду.
- RU+EN локализация, доступность кнопок и фокус, мобильный UI, без чужих цветов/визуального ребрендинга.

Пример (не включать личную реальную беседу пользователя в публичные тестовые фикстуры): взрослый ребёнок отстаивает приватность переписки. Собеседник-родитель в итоге явно признаёт право на приватность, отделяет благодарность за помощь от доступа к сообщениям и отказывается от требования; это сильный кандидат achieved. Если родитель лишь смягчил тон, но продолжает требовать переписку — НЕ achieved.

## Задача C — PDF в текущем визуальном языке приложения
Сделать действие `Сохранить в PDF` в итоговом экране:
1) Если пользователь запросил и получил фидбек: PDF включает публичное описание кейса, роли, цели, контекст, известные факты, участников, ПОЛНЫЙ реально сохранённый диалог игрок/собеседник, затем **с новой страницы** структурированный существующий фидбек: summary, strengths, risks, next_step, example_phrase.
2) Если пользователь отказался от фидбека: предложить `Сохранить кейс в PDF`; PDF содержит кейс и всю переписку БЕЗ страницы фидбека, без создания пустого/синтетического отзыва и БЕЗ какого-либо запроса к Judge.
3) Если фидбек завершился ошибкой: позволить сохранить существующий диалог без него и повторить разбор по прежнему пути.
4) Длинная переписка может занимать сколько нужно страниц. Не обрезать сообщения, переносить длинные слова/строки и блоки без пересечений; секцию фидбека начинать с новой страницы, если она присутствует. Не ставить жёсткий лимит «2 страницы».
5) Дизайн: A4, фирменные цвета существующего сайта (`#243B5A`, `#AE432F`, `#202B3E`), аккуратная типографика, логотип/wordmark только из разрешённых локальных assets, header/footer с пагинацией, красивое разделение ролей в диалоге, читабельность в печати. Встроенные/подключённые легальные шрифты с полноценной кириллицей и латиницей, корректные «кавычки», тире и RU/EN. Полноценный текстовый searchable PDF, а не один большой скриншот.
6) Надёжнее делать PDF по данным на сервере (например `GET /api/sessions/{id}/export.pdf` с `application/pdf` и безопасным `Content-Disposition`; endpoint должен проходить текущий DemoGuard), либо обосновать безопасную равноценную архитектуру. Если endpoint отсутствует — реализовать и тестировать его. Никакого доступа к `runtime_case`/private_facts, внутренним инструкциям, API-ключам, прокси credentials, приватным hidden criteria. Сохранять только данные из уже разрешённого публичного snapshot и готового approved debrief. Отдельные случаи pending/failed/cancelled сообщений оформить прозрачно: например обозначить статус, не выдавать за полученный ответ.
7) Файл скачивается браузером с нормальным именем без персональных/потенциально опасных символов; работает через HTTP Basic и на мобилке; download не должен запускать Judge или любые другие модели. Использовать существующие доступные зависимости или явно документировать минимальную новую; не тянуть внешние CSS/шрифты с сети во время экспорта.
