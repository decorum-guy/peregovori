# Qwen3-14B на Intelion RTX3090: BASE → VRAM preflight → QLoRA E1/E2 → DEV

**Статус 14.10.2026: код подготовлен и закоммичен, GPU-эксперимент ещё не запускался.** Нельзя заранее гарантировать, что одна RTX3090/24GiB VRAM вместит *обучение* Qwen3-14B: успешная **4-bit инференция не является проверкой backward и оптимизатора**. Реальная проверка — один шаг обучения на самом длинном SFT-примере, с запасом >1 GiB свободной VRAM. Это **4-bit QLoRA**, НЕ полный fine-tuning всех 14B весов.

## Зачем / гипотеза

Существуют 200 зафиксированных TRAIN-кейсов и 895 next-message supervised targets. В текущем диагностическом эксперименте их **НЕ расширяем**, DEV/TEST **НЕ используем для обучения**. По сравнению 8B V2 на DEV прибавка к V1 есть, но остаются role inversion, hard-limits, арифметика и смешанные конфликты; источник может быть **и в ёмкости backbone, и в размере/разметке TRAIN, и в состоянии/валидации игры**. Увеличение 14B позволит получить полезные признаки, но не математически доказать единственную причину.

**Заранее зафиксированные три версии для слепого сравнения:**
1. **14B BASE**, без LoRA: прежние замороженные 25 DEV-кейсов / 75 проб, greedy non-thinking, max 192 tokens.
2. **14B QLoRA rank16, эпоха 1**: снимок адаптера после первой полной эпохи.
3. **14B QLoRA rank16, эпоха 2**: снимок после второй полной эпохи **того же самого непрерывного двухэпохового запуска**.

Если ранее сохранённые 75 ответов 8B V2 присутствуют — они добавляются как четвёртая слепая колонка. **Примечание о чистоте эксперимента:** эпоха 1 здесь является моментальным снимком из 2-эпохового плана с общим косинусным LR; это НЕ независимый запуск с косинусной кривой, заканчивающейся после 1 эпохи. Такой подход сохраняет сопоставимость шагов и экономит GPU.

## Бюджет / ограничения

Тот же Intelion cloud VM **11425**, 1×RTX3090 24 GiB, системная RAM 32 GiB, диск 128GB в прежней конфигурации. План пользователя — бюджет примерно **5 часов с момента загрузки VM**. Launcher устанавливает **265-минутный in-VM cloud API watchdog** *после быстрых проверок*, оставляя запас к пяти часам на запуск VM и мелкие накладные расходы. Реальное обучение 14B на 24GB и скорость **не проверены**. При OOM, нехватке места, отсутствии DEV или PAT — не тратим оставшееся время на повторные попытки и стараемся остановить VM.

**Перед запуском:** отключить Intelion **Auto-renew** в кабинете. Биллинг начинается при включении GPU-машины, а не с начала скрипта. Если подготовка/подключение заняла значимое время, вручную сократить бюджет/выключить раньше. Бэкап в GitHub может сорваться из-за сети — файлы остаются на VM-диске, автоматическая остановка сохраняется.

## Как начать — на той же VM после её включения

Приватный репозиторий уже должен быть настроен: **decorum-guy/private-peregovori**, доступ по PAT в `~/.config/peregovori/github_artifacts.json` на этой VM. Публичная ветка `main` содержит скрипты. Никаких DEV/TEST в публичный GitHub.

```bash
cd /root/peregovori
git switch main
git pull --ff-only
source .venv/bin/activate
python training/upload_private_release.py check
bash training/start_14b_epochs.sh
```

Если Git обнаруживает незакоммиченные пользовательские изменения, **НЕ делать `reset --hard`**, сохранить их или сообщить перед pull.

### Что делает `start_14b_epochs.sh`

**До постановки таймера:** py_compile, tmux/nvidia-smi, наличие frozen DEV/старых результатов, `PRIVATE repo verified`, **не менее 40GiB свободного места**, проверка отсутствия других GPU-тренировок и живого старого watchdog.

**После постановки таймера (265 минут):** tmux `qwen14b-epochs` запускает:
1. **14B BASE**: 75 DEV-проб. Нет LoRA и никакого изменения TRAIN. Сохраняет ответы по мере генерации.
2. **CUDA/OOM preflight:** реальный градиент/шаг AdamW на 14B NF4 QLoRA с самым длинным TRAIN-примером (наша предыдущая TRAIN-статистика: 2224 токена), `rank=16`, batch1, grad_acc8, gradient checkpointing, минимум 1GiB свободной VRAM после шага. **Не путать с проверкой только model.load.**
3. **Непрерывное QLoRA 2 эпохи** с двумя автономными снимками `adapter_epoch_1` и `adapter_epoch_2`; обязательная реальная отметка `actual_epoch`, раздельные .safetensors. При нехватке времени сохранить E1, **не называть частичную E2 полной**.
4. **DEV E1 / E2:** генерирует отдельные 75 ответов каждой версии на тех же префиксах, оппонент видит только roleplayer контекст, не видит teaching/oracle.
5. **Слепой CSV** для последующего независимого содержательного судьи; **автоматическая сводка лишь техническая и не доказывает переговорное качество**.
6. **GitHub Private Release:** сохраняет оба адаптера с SHA-256 (если созданы), DEV ZIP/tar, отчёты и логи. Затем запрашивает STOP Intelion; резервный watchdog останавливает и при зависании/ошибках.

Если E1 или E2 не успеют, выгрузка **частичных** результатов и немедленный stop имеют приоритет над повторным обучением. Порог остановки обучения: 55 минут до hard-stop, чтобы оставить время для DEV и выгрузки. Интервал фактических вычислений в пределах 5h не гарантируется, только ограничивается.

## Критерий успеха

Подтверждённый trainable NF4 на RTX3090 (включая longest sequence + optimizer state, достаточный запас VRAM) и три **полных** набора по 75 DEV-ответов. Затем **слепая содержательная проверка по методологии**. Если 14B BASE уже существенно лучше 8B V2 и E1/E2 не добавляют качества, большая часть ограничения может объясняться исходной ёмкостью; если 14B E1/E2 также сохраняют те же ошибки, проверять DATA + внешнее состояние игры. Результат DEV сам по себе не является финальным доказательством — после выбора последнего кандидата понадобится запечатанный TEST и многоходовые игры.
